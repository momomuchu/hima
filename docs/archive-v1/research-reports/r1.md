Oui. Ce que tu cherches, c’est une **phase de clarification exhaustive avant développement**, dont le but est de supprimer l’implicite.

L’objectif n’est pas encore de construire.
L’objectif est de produire un dossier suffisamment clair pour que l’équipe puisse développer sans ambiguïté majeure.

Je l’appellerais :

# Phase 0 — Clarification complète avant développement

## 1. Idée initiale

À expliciter :

* Quelle est l’idée ?

* Quelle valeur attend-on ?

## 5. Usage prévu

But : définir exactement ce que le logiciel doit faire, et surtout ce qu’il ne doit pas faire.

À expliciter :

* À quoi sert le logiciel ?
* Dans quel contexte est-il utilisé ?
* Par qui ?
* Pour quels patients ou dossiers ?
* Pour quelles décisions ?
* Avec quelles limites ?
* Quelles décisions restent humaines ?
* Le logiciel informe-t-il ?
* Le logiciel calcule-t-il ?
* Le logiciel recommande-t-il ?
* Le logiciel automatise-t-il une action ?
* Le logiciel influence-t-il une décision médicale ?
* Le logiciel peut-il être utilisé hors contexte ?
* Quels usages sont interdits ?

Livrable :

```text
Usage prévu
- Le logiciel est destiné à...
- Il est utilisé par...
- Dans le contexte de...
- Il permet de...
- Il ne permet pas de...
- Il ne remplace pas...
- Les décisions finales restent...
```

Exemple :

```text
Le logiciel est destiné à faciliter la consultation des transmissions infirmières validées dans une unité hospitalière.

Il ne fournit pas de diagnostic, ne recommande pas de traitement, ne priorise pas les patients selon un risque médical et ne remplace pas le jugement clinique.
```

C’est une section essentielle parce qu’elle réduit énormément les ambiguïtés.

## 7. Parcours utilisateur

But : rendre les usages concrets.

À expliciter pour chaque parcours :

* Déclencheur.
* Utilisateur.
* Objectif.
* Préconditions.
* Étapes.
* Données affichées.

* Décisions possibles.
* Messages d’erreur.
* Cas limites.
* Permissions.
* Résultat attendu.

Format recommandé :

```text

Acteur :
Infirmier

Préconditions :

- L’utilisateur a accès à l’unité du patient.
- Le patient existe.
- Une transmission validée existe.

1. L’utilisateur recherche le patient.
2. Le système affiche les patients autorisés.
3. L’utilisateur sélectionne le patient.
4. Le système affiche les transmissions validées.

L’utilisateur consulte uniquement les transmissions auxquelles il a droit.

Cas d’erreur :
- Patient introuvable.
- Accès refusé.
- Transmission inexistante.
- Service indisponible.
```

## 8. Règles métier

But : sortir les règles de la tête des experts métier.

À expliciter :

* Conditions d’affichage.
* Conditions de modification.
* Conditions de suppression.
* Conditions de validation.
* Conditions d’archivage.
* Règles de calcul.
* Règles de priorité.
* Règles de notification.
* Règles de responsabilité.
* Règles d’accès.
* Règles de conservation.
* Règles d’audit.
* Règles d’exception.

Format recommandé :

```text
Règle métier RM-001
Titre :
Consultation des transmissions

Règle :
Un utilisateur ne peut consulter que les transmissions des patients rattachés à une unité à laquelle il est autorisé.

Justification :
Protection des données patient.

Exceptions :
Aucune, sauf profil administrateur habilité.

Tests attendus :
- Utilisateur autorisé : accès accordé.
- Utilisateur non autorisé : accès refusé.
- Patient hors périmètre : accès refusé.
```

Chaque règle métier importante doit avoir au moins un test associé.

## 17. Critères d’acceptation

But : rendre la validation objective.

Chaque fonctionnalité doit avoir des critères testables.

Format recommandé :

```text
Fonctionnalité :
Consultation des transmissions

Critères d’acceptation :
- Étant donné un utilisateur autorisé, quand il ouvre le dossier patient, alors il voit les transmissions validées.
- Étant donné un utilisateur non autorisé, quand il tente d’ouvrir le dossier patient, alors l’accès est refusé.
- Étant donné une erreur serveur, quand la transmission ne peut pas être chargée, alors un message d’erreur clair est affiché.
- Toute consultation réussie est journalisée.
```

Un bon critère d’acceptation est :

* clair ;
* vérifiable ;
* non ambigu ;
* testable ;
* lié à une règle métier ;
* lié à un risque si nécessaire.

# Le principe clé

Pour éviter l’implicite, chaque élément doit être classé dans une des catégories suivantes :

```text
Défini
Non défini
Non applicable
À confirmer
Risque accepté
Hors périmètre
Bloquant
```

Ce système évite les faux accords.

Par exemple, au lieu de dire :

> On verra plus tard la gestion des droits.

Il faut écrire :

```text
Gestion des droits : À confirmer
Responsable : DSI + métier
Impact : bloquant avant développement backend
Décision attendue : avant conception technique
```

---

# Phrase de référence

La phase avant développement doit permettre de dire :

> Tout ce qui est nécessaire au développement est soit défini, soit explicitement non applicable, soit identifié comme une décision ouverte avec un responsable, un impact et une échéance.

C’est ça qui supprime l’implicite.
